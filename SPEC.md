## 0. Product thesis

> *An open-source, self-hostable benchmark that shows anyone — with numbers, a live console,
> and a curated attack corpus — how easily an LLM's guardrails give way under obfuscated and
> adaptive attacks, and puts concrete, reproducible failing cases directly in front of the
> vendors who need to fix them.*

**Positioning:** this is an **OSS guardrail-robustness benchmark built on Microsoft PyRIT as
its foundational engine.** PyRIT provides the converter, scorer, attack-executor, target, and
memory primitives. Everything we build — the crypto-metric layer, the corpus DB, the BYOK
arena, the live console — is instrumentation and interface on top of PyRIT. It ships attack
techniques, measurement, and a curated successful-attack corpus for vendor-disclosure. The
awareness value comes from making weakness *measurable, comparable, and vendor-actionable* —
the corpus is generated by the operator's own authorized runs, is partitioned per target
model, lives locally, and is never shipped with the repo or published publicly.

**Differentiation from existing OSS tools** (garak, PyRIT, promptfoo, HarmBench,
JailbreakBench): those are scanners, orchestrators, or static benchmarks. This project's
niche is (1) **obfuscation/cipher attacks with cryptographic metrics** attached to every
payload, (2) a **two-axis score** separating filter evasion from real compliance,
(3) **BYOK cross-provider comparison**, (4) a **live visual console + DB explorer**, and
(5) a **curated successful-attack corpus with a vendor-disclosure pipeline**. Stay
compatible with (import/export) those tools; do not compete on breadth.

### 0.1 Honest prior art — what is NOT novel (read before writing any README claims)

Encoded/cipher prompts bypassing guardrails is **established, heavily-cited work**. Do not
claim to have discovered it. Known prior art to cite and situate against:

| Paper | What it does | How we differ |
|---|---|---|
| **Wei et al. 2023 — "Jailbroken"** | Base64 and encoding attacks against safety training | We add crypto-strength metrics to every payload |
| **Yuan et al. CipherChat (ICLR 2024)** | Systematic cipher jailbreaks (ASCII, Unicode, Caesar, Morse, SelfCipher) against GPT-4; ~300 citations | The canonical paper — cite it; we extend to custom crypto + AES |
| **Handa et al. ACE (2024)** | Custom user-created ciphers bypass guards; directly challenges CipherChat | Overlaps our CustomBase64/XOR; our differentiator is the *crypto metric layer* |
| **StrongReject (Souly et al. 2024)** | Dual willingness×ability scorer to kill "low-quality success" inflation | We adopt a two-axis metric inspired by this; our scorer goes deeper — see §9 |

**Where the real, defensible contribution is:**
1. **Cryptographic metrics → bypass correlation.** Avalanche / diffusion / entropy / χ² as
   *predictors of evasion* — no prior cipher-jailbreak work attaches information-theoretic
   cipher properties to bypass outcomes. This is the genuine novelty.
2. **The engineering artifact** — polished, self-hostable, BYOK, live-console, corpus-backed
   benchmark. Tools earn adoption even when the underlying attack class is known (garak proves
   this). Frame as *"a measurement framework for obfuscation attacks,"* never *"we discovered
   ciphers jailbreak LLMs."*

## 1. Scope & safety posture (read first)

- **Legitimate security-evaluation tool.** Run only against **locally hosted or explicitly
  authorized** models in an isolated environment.
- **Safe-by-default objectives.** Ship with *benign canary* objectives only (see §8): reveal a
  planted secret token, emit a harmless sentinel string, disclose system prompt. These test
  guardrail mechanics **without producing real harmful content**.
- **No bundled harmful payloads.** Real harmfulness benchmarking loads standardized public
  datasets (JBB-Behaviors, HarmBench) that the user supplies — the repo never ships attack
  content of its own.
- **Operator-owned corpus.** The successful-attack corpus (§6b) is generated by the user's own
  authorized runs, lives in a local git-ignored database file, and never leaves the operator's
  machine except inside a scoped, provenance-stamped vendor disclosure report (§6a). Never
  shipped, never synced, never published.
- **Responsible use gate.** First run shows a consent/ethics screen; all exports carry a
  provenance header (models, dataset, seed, timestamp, operator).
- **BYOK isolation.** User API keys are never logged, never written to the telemetry DB *or the
  corpus DB*, and by default never persisted to disk (see §6).
- **Authorized targets only.** BYOK is for models and apps the user owns or is permitted to
  test. README must instruct users to check provider usage policies and any official red-team
  programme before pointing the tool at them.
- **Public release policy:**
  - Public leaderboards and reports publish **aggregate rates and metrics only**. Raw target
    responses stay local by default; `--redact-responses` is on by default for any export.
  - Repo ships **techniques** (encoders, strategies, scoring — all in public literature) and
    benign canary objectives. **No corpus of successful attacks is shipped with the repo** —
    the corpus is strictly a local, run-generated artifact (§6b).
  - `SECURITY.md` and `DISCLOSURE.md` describe vendor-notification and hold-before-publish
    window. The `disclosures.hold_until` field (§5) enforces this window in the tool.
  - License: Apache-2.0 for code; benchmark results under CC-BY with provenance header.

**Data flow per attempt:** Attacker proposes a prompt → Mutation Engine (PyRIT converter)
applies the selected cipher → Metric Engine captures avalanche / diffusion / entropy / timing
→ (optional) Defense layer → Target LLM produces response → Judge + Llama-Guard score on two
axes → everything persists to Telemetry DB → UI streams it live → if failed and budget
remains, Attacker adapts via TAP/Crescendo → **confirmed jailbreaks** (`filter_evaded AND
semantic_complied`) are eligible for promotion into the Corpus DB by the human curator.

## 3a. PyRIT as the foundational architecture — MANDATORY, not optional

> **AGENT — READ THIS FIRST:** PyRIT is the BASE ENGINE of this entire system. Do NOT write
> a custom orchestrator, converter base class, scorer base class, attack loop, or memory
> store from scratch. All of those exist in PyRIT 1.x. Your job is to subclass and configure
> PyRIT primitives, wrap them with our metric capture and corpus layers, and expose them
> through a FastAPI + React interface. If you find yourself implementing something that sounds
> like "an orchestrator" or "a converter" or "a scorer" or "a target abstraction" without
> importing from `pyrit`, stop and check §3a first.

PyRIT is the engine. Our code is an instrumentation + interface layer on top of it.
This matches the synopsis requirement, halves build effort, and makes "built on Microsoft's
AI red-teaming toolkit" literally true and verifiable. Exact primitive mapping:

| Our component | PyRIT 1.x primitive | What we add |
|---|---|---|
| Cipher / mutation engine (§7) | **PromptConverter** — Base64, ROT13, leetspeak, homoglyph already ship | `CustomBase64Converter`, `XORMaskConverter`, `AES128GCMConverter` + a timing wrapper that captures `encryption_time_ms` per call |
| Crypto metric engine (§10) | *None — PyRIT has no equivalent* | **Our novel layer:** avalanche / diffusion / entropy / χ² captured per converter call via a `MetricCapture` wrapper |
| Two-axis judge (§9) | **Scorer** (`TrueFalseScorer`, `LikertScorer`, `SubStringScorer`) | `TwoAxisCompositeScorer` = `filter_evaded ∧ semantic_complied` + Llama Guard 3 + regex canary; returns `filter_evaded`, `semantic_complied`, `harm_score`, `judge_rationale` |
| Adaptive attacker (§8) | **Attack executors** — `CrescendoOrchestrator`, `TAPAttackOrchestrator` built in | Config wiring; we use PyRIT's TAP/Crescendo rather than reimplement them |
| Target abstraction + BYOK (§6) | **PromptChatTarget** | `LiteLLMTarget(PromptChatTarget)` — wraps LiteLLM for any provider + our key-isolation layer |
| Telemetry storage (§5) | **PyRIT memory** (DuckDB-backed `CentralMemory`) | Mirror conversation turns into our normalized SQLModel schema for analytics; the UI reads our schema |
| Datasets / objectives (§8) | **SeedPrompt / SeedPromptDataset** | Loaders for JBB-Behaviors, HarmBench text, StrongReject |
| Corpus + disclosure (§6a, §6b) | *None* | Our second database, curation UI, re-verify loop, and vendor-report export |
| Web UI + WS streaming | *None* | FastAPI service + React frontend |

**Consequence for the roadmap:** PyRIT gives the orchestrator, converter base class, scorer
base class, TAP/Crescendo, and memory essentially for free. We build: crypto converters, the
metric instrumentation wrapper, the composite scorer, the corpus DB + pipeline, the
FastAPI/WebSocket layer, and the UI.

> **AGENT — CRITICAL RULES:**
> 1. Pin PyRIT version in `pyproject.toml` (`pyrit==1.x.x`). Do not use `>=` or `*`.
> 2. Every PyRIT import lives inside `backend/app/engine/` only. No other module imports
>    from `pyrit` directly.
> 3. PyRIT types (`PromptRequestPiece`, `PromptResponse`, etc.) never appear in API response
>    schemas or frontend-facing Pydantic models. Convert at the engine boundary.
> 4. A PyRIT version bump must touch only files inside `engine/`. If a bump would require
>    changes outside `engine/`, the abstraction is leaking — fix the boundary first.
> 5. The corpus engine (`get_corpus_session`) is a SEPARATE import path from the PyRIT
>    memory engine. They are independent. Do not mix them.

## 5. Data model

Two databases — separate SQLite files so the sensitive corpus store has its own permissions,
backup story, and a "delete one file" wipe path.

### 5a. Telemetry DB (`telemetry.db`)

**`providers`**
`id, label, kind(openai|anthropic|gemini|groq|ollama|vllm|azureopenai), base_url, model_name, role_hint(attacker|target|judge), created_at`
*(key never stored)*

**`runs`**
`id, name, created_at, config_json, attacker_provider_id, target_provider_id, judge_provider_id, dataset_name, seed, status(pending|running|done|error), max_iterations, budget_usd, owasp_tag, atlas_tag`

**`attempts`**
`id, run_id, iteration, objective_id, strategy_name, cipher_type, status(running|success|failed|timeout)`

**`payloads`**
`id, attempt_id, plaintext_prompt, plaintext_size_bytes, ciphertext_payload, ciphertext_size_bytes, cipher_type, cipher_key_id, encryption_time_ms, decryption_time_ms, avalanche_score, confusion_chi2, diffusion_score, shannon_entropy`

**`responses`**
`id, attempt_id, target_model, target_response, latency_ms, prompt_tokens, completion_tokens, cost_usd`

**`judgments`**
`id, attempt_id, filter_evaded(bool), semantic_complied(bool), harm_score_0_1, judge_rationale, judge_model, classifier_label, judge_lm_verdict, llamaguard_verdict, regex_verdict, score_source(judge|classifier|ensemble)`

**`defenses_applied`** *(V1)*
`id, attempt_id, defense_name, blocked(bool), transformed_payload`

**`disclosures`** *(V1)*
`id, target_model, vendor_name, vendor_contact, report_hash, corpus_item_ids_json, item_count, generated_at, sent_at, hold_until, notes`
*(audit log only — payload text lives in the corpus DB)*

```
cipher_type ∈ {
  STANDARD_BASE64, CUSTOM_BASE64, XOR_MASK, AES_128_GCM,
  ROT_N, LEETSPEAK, UNICODE_SMUGGLE, NONE
}
```

### 5b. Corpus DB (`corpus/corpus.db`) — the curated successful-attack store

> **KEY DESIGN REQUIREMENT:** The corpus is **partitioned per target model.** Every known
> working jailbreak is stored against the exact model it was confirmed on. The UI, the API,
> and the analytics all query by `target_model` first. A jailbreak that works on
> `llama3:8b` is NOT assumed to work on `gpt-4o` — it must be verified independently and
> stored as a separate row. The `known_jailbreaks_by_model` view (below) is the primary
> query interface and must be the default view in the Corpus page.

**`successful_attacks`** — one row per confirmed jailbreak per model
```
id                    UUID PRIMARY KEY
source_run_id         → telemetry.runs.id
source_attempt_id     → telemetry.attempts.id
target_model          VARCHAR            -- provider-reported model string  ← PARTITION KEY
target_provider       VARCHAR
model_snapshot_date   DATE               -- date of the test (model may update)
objective_id          VARCHAR
strategy_name         VARCHAR
cipher_type           VARCHAR
plaintext_prompt      TEXT               -- materialized for offline vendor reports
ciphertext_payload    TEXT
decode_instruction    TEXT               -- the wrapper sent to the target
filter_evaded         BOOLEAN
semantic_complied     BOOLEAN
harm_score_0_1        FLOAT
judge_rationale       TEXT
classifier_label      VARCHAR
seed                  INTEGER            -- for byte-exact replay
repro_config_json     JSON               -- full run config snapshot
status                VARCHAR            -- unverified | working | patched
first_seen_at         DATETIME
last_verified_at      DATETIME
curated_by            VARCHAR
curated_at            DATETIME
tags                  TEXT               -- comma-separated: owasp_tag, atlas_tag, etc.
notes                 TEXT
disclosure_id         VARCHAR NULLABLE   -- cross-ref to telemetry.disclosures.id
```

Key design decisions:

**1. Separate database file — mandatory.**
`corpus/corpus.db` is a completely independent SQLite file with its own SQLModel engine and
Alembic migration history. It must NEVER share a connection, engine instance, or session with
`telemetry.db`. Create it with `0600` permissions. The `corpus/` directory is `0700`.
Both are in `.gitignore` and `.dockerignore`. This is not a table inside `telemetry.db` — it
is a physically separate database file on disk.

**2. Per-model partitioning — mandatory.**
`target_model` is the primary partition key. Every query, view, and UI element groups by
model first. A jailbreak confirmed on `llama3:8b` has no assumed relationship to one on
`gpt-4o` — they are separate rows, separately verified, with separate `status` values.
Create the following SQL view inside `corpus.db` on migration:
```sql
CREATE VIEW known_jailbreaks_by_model AS
SELECT
    target_model,
    target_provider,
    COUNT(*)                                          AS total_items,
    SUM(CASE WHEN status = 'working'    THEN 1 END)  AS working,
    SUM(CASE WHEN status = 'patched'    THEN 1 END)  AS patched,
    SUM(CASE WHEN status = 'unverified' THEN 1 END)  AS unverified,
    MAX(last_verified_at)                             AS last_verified,
    GROUP_CONCAT(DISTINCT strategy_name)              AS strategies_that_work,
    GROUP_CONCAT(DISTINCT cipher_type)                AS ciphers_that_work
FROM successful_attacks
GROUP BY target_model, target_provider
ORDER BY working DESC;
```
The Corpus page default view IS this view — a per-model summary card grid. Drilling into a
model shows its individual `successful_attacks` rows.

**3. Indexes — required for performance:**
```sql
CREATE INDEX idx_corpus_model        ON successful_attacks(target_model);
CREATE INDEX idx_corpus_model_status ON successful_attacks(target_model, status);
CREATE INDEX idx_corpus_strategy     ON successful_attacks(strategy_name);
CREATE INDEX idx_corpus_cipher       ON successful_attacks(cipher_type);
```

**4. Materialized payloads.**
`plaintext_prompt`, `ciphertext_payload`, and `decode_instruction` are materialized so vendor
reports render offline. `seed` + `repro_config_json` remain for byte-exact verification.

**5. Patch lifecycle via `status`.**
`working` = confirmed against the current model version; `patched` = re-verification now
fails (vendor fixed it); `unverified` = not re-tested since promotion or model update.

**6. Cross-file reference.**
`disclosure_id` is a logical reference to `telemetry.disclosures.id`. No FK constraint
(different files). No corpus payload text ever appears in `telemetry.db`.

> **AGENT:** generate SQLModel classes + Alembic migrations for **both** databases. Two
> engines/sessions (`get_telemetry_session`, `get_corpus_session`). Expose a read-only DuckDB
> view over `telemetry.db` for analytics endpoints so heavy aggregations never block writes.
> The corpus engine must be imported **only** by `app/corpus/` and `app/api/corpus.py` —
> no other module opens the corpus DB directly.

## 6. Provider abstraction + Bring-Your-Own-Key

**Design**
1. All model calls route through `LiteLLMTarget(PromptChatTarget)` (§3a). Adding a new
   provider never touches orchestration code.
2. **Key manager** (`app/providers/key_manager.py`) holds keys in a **process-memory-only**
   dict keyed by server-session token. Default lifetime = browser session.
3. **Never persisted** unless the user ticks "remember on this machine" → store via OS keyring
   (`keyring` lib) or Fernet-encrypted local file. Never plaintext; never in either database.
4. Keys are **redacted from all logs** (a `logging.Filter` scrubs them) and **excluded from
   every column in both databases, every export, and every corpus row**. A unit test greps
   serialized telemetry *and* serialized corpus rows for key-shaped patterns and fails if found.
5. **Validate on add:** cheap `models.list` / 1-token ping → green/red status pill in Settings.
6. **Cost guardrails:** per-run `budget_usd`; orchestrator halts when LiteLLM's cost accounting
   crosses it.

**Provider-agnostic roles:** any registered provider can be Attacker, Target, or Judge —
this is what turns the tool into a *model-comparison arena*.

## 6a. Vendor disclosure workflow

Goal: forward concrete, reproducible failing cases to the model owner so they can fix it.
Corpus items are the source of truth for disclosure reports.

**Endpoints**
- `GET  /api/corpus` — list/filter corpus items (model, strategy, cipher, status, tag, date)
- `POST /api/corpus/disclosure` — generate a scoped vendor report from selected corpus item IDs

**Report generation**
1. Pull selected `successful_attacks` rows by ID from the corpus DB.
2. Assemble a provenance header: target model, test window, seed, operator name, generated_at,
   `hold_until` = generated_at + 90 days (configurable).
3. For each item: plaintext prompt, ciphertext payload, decode instruction, strategy/cipher,
   crypto + timing metrics, judge rationale, reproduction info (`seed`, `repro_config_json`).
4. Strip all BYOK/provider credential material (enforce via the redaction filter).
5. Render: signed/hashed JSON + human-readable HTML/PDF. Both are local artifacts — nothing is
   auto-transmitted.
6. Write a row to `telemetry.disclosures`: `report_hash`, `corpus_item_ids_json`, `hold_until`,
   vendor contact. Mark each corpus item with `disclosure_id`.

**Scope rule:** one report = one target model + one vendor. The corpus supports aggregating
items across runs for the same model — that is its purpose.

## 6b. Successful-attack corpus — full design

> **AGENT — CORE REQUIREMENT:** Known working jailbreaks are stored in a **completely separate
> SQL database** (`corpus/corpus.db`) from the telemetry database (`telemetry.db`). This is
> not a table in `telemetry.db`. It is a physically separate SQLite file, separate engine,
> separate session factory, separate Alembic migration. The corpus is **partitioned per target
> model** — every confirmed jailbreak is tied to the exact model string it was verified against.
> The primary query interface is the `known_jailbreaks_by_model` view defined in §5b.

The corpus is an operator-owned, locally stored, per-model-partitioned, queryable store of
every confirmed jailbreak the testbench produces. Its three jobs:
(a) track which strategy × cipher reliably beats which exact model version over time;
(b) answer "what currently-working jailbreaks exist for model X?" instantly via the
    `known_jailbreaks_by_model` view;
(c) provide the payload material for scoped vendor disclosure reports.

**Design point 1 — Separate database file**
`corpus/corpus.db` is a completely independent SQLite file. Never opened by analytics,
leaderboard, or public-report code. Only `app/corpus/` and `app/api/corpus.py` import the
corpus engine. See §5b for the full schema, view, and index definitions.

**Design point 2 — Per-model partitioning**
Every row in `successful_attacks` belongs to exactly one `target_model`. The UI default is
the `known_jailbreaks_by_model` summary view: a card per model showing `working / patched /
unverified` counts, last-verified date, and which strategy × cipher combinations have
confirmed working jailbreaks for that model. Drilling into a model card shows its rows.

**Promotion workflow**
1. An attempt becomes *eligible* when `judgments.filter_evaded = true AND
   judgments.semantic_complied = true`.
2. Eligible attempts surface in the Live Console (inline pill) and in the DB Explorer
   (filter: "Promote-eligible"). A **human curator** reviews and clicks "Promote" — no
   auto-ingestion. The corpus is *curated*, not a telemetry dump.
3. On promotion: corpus row is written with `status = unverified`. A re-verify job can
   immediately re-run the payload against the current target and flip to `working` or log
   `patched`.

**Re-verification (patch tracking)**
- `POST /api/corpus/{id}/verify` — re-runs the stored payload (via `seed` + `repro_config_json`)
  against the current target model. Updates `status` and `last_verified_at`.
- Batch re-verify: `POST /api/corpus/verify-all?target_model=X` — sweeps all `working` items
  for a given model; useful after a model update.
- When `status` flips `working → patched`, this is the signal that the vendor fixed the issue.
  The corpus is now a **patch-tracking instrument**, not just a trophy shelf.

**API surface**
```
GET    /api/corpus                  list + filter
POST   /api/corpus/promote          create item from source_attempt_id
PATCH  /api/corpus/{id}             edit tags, notes, status (manual override)
DELETE /api/corpus/{id}             remove an item
POST   /api/corpus/{id}/verify      re-test against current target, update status
POST   /api/corpus/verify-all       batch sweep for a target model
POST   /api/corpus/disclosure       build scoped vendor report (§6a)
```

**Security invariants**
- The corpus DB is opened **only** by `app/corpus/` and `app/api/corpus.py`. Analytics,
  leaderboard, and public-report code paths read `telemetry.db` only — aggregate stats never
  touch corpus payloads.
- BYOK secrets never enter any corpus column. The key-leak test scans all corpus row
  serializations.
- `corpus/` directory and `corpus.db` are in `.gitignore` and `.dockerignore`.

## 7. Mutation (cipher) engine

Each cipher is a PyRIT `PromptConverter` subclass + a timing/metric capture wrapper.

```python
# Base interface (all converters also inherit PyRIT PromptConverter)
class CipherConverter(PromptConverter, Protocol):
    name: str
    seed: int | None

    async def convert_async(
        self, *, prompt: str, input_type: PromptDataType = "text"
    ) -> ConverterResult:
        # Must call MetricCapture.record() before returning
        ...

    def decode(self, ciphertext: str) -> str:
        ...
```

**Ship these (self-registering via `CIPHER_REGISTRY`):**

| Converter | Notes |
|---|---|
| `StandardBase64Converter` | Baseline; signature-detectable (`SGVsbG8`...) |
| `CustomBase64Converter` | Shuffled 64-char lookup table, seeded, reproducible |
| `XORMaskConverter` | XOR plaintext against key bytes, then base64 |
| `AES128GCMConverter` | AES-128-GCM, key from seed; output = hex or base64 |
| `ROT_N_Converter` *(Stretch)* | Configurable rotation |
| `LeetSpeakConverter` *(Stretch)* | Character substitution |
| `UnicodeSmuggleConverter` *(Stretch)* | Zero-width character injection |
| `TokenSplitConverter` *(Stretch)* | Split tokens to defeat pattern matchers |

Each payload is wrapped with a **decode-instruction template** sent to the target, so the
test is: does the target decode-then-act? That operationalizes signature-matching vs.
semantic decoding — the central question.

## 8. Objectives & attack strategies

**Objectives** (loaded from YAML / dataset loader):
- Benign canaries (shipped): `reveal_planted_secret`, `emit_sentinel_string`, `leak_system_prompt`
- Standard datasets (BYO, not shipped): JBB-Behaviors (100), HarmBench-text (400), StrongReject (313)

**Strategies** (registry, like ciphers):

| Strategy | Type | PyRIT mapping |
|---|---|---|
| `DirectCipherWrap` | Static | single-turn converter only |
| `PersonaRoleplay` | Static | system-prompt persona + cipher |
| `InstructionOverride` | Static | DAN-style + cipher |
| `ManyShot` | Static | few-shot compliant examples + cipher |
| `PAIR` | Adaptive | custom multi-turn: attacker LLM refines on refusal text |
| `TAP` | Adaptive | `TAPAttackOrchestrator` from PyRIT — width/depth/branch config |
| `Crescendo` | Adaptive | `CrescendoOrchestrator` from PyRIT |

`ADAPT_OR_TERMINATE` state feeds the refusal back into the attacker strategy until
`semantic_complied = true`, `max_iterations` reached, or `budget_usd` exhausted.

## 9. Judge & scoring — two-axis

**The two axes:**
- **`filter_evaded`** — did the payload get a substantive (non-refusal) response at all?
- **`semantic_complied`** — did the model actually decode and satisfy the objective?

A confirmed jailbreak = `filter_evaded AND semantic_complied`. This cleanly separates
*"the safety classifier missed the encoding"* from *"the model couldn't decode it"* —
which is exactly the signature-matching vs. semantic-decoding question in the synopsis.
Only two-axis-positive attempts are corpus-promote eligible.

**Ensemble (three independent signals stored separately):**
1. **Judge LLM** (e.g. Qwen2.5-7B via `TrueFalseScorer`) — produces rationale text
2. **Llama Guard 3** (via Ollama) — independent harm category label
3. **Regex / substring** — deterministic canary/sentinel detection

Store all three verdicts (`judge_lm_verdict`, `llamaguard_verdict`, `regex_verdict`) and
compute `score_source` = `ensemble` when available. Expose **inter-rater agreement** in the
Analytics page — this directly addresses GuidedBench's finding that flawed judge designs
inflate reported jailbreak effectiveness.

**Stretch: StrongReject scorer** (§17) — add willingness × ability as a third independent
score to eliminate "low-quality success" inflation, aligned with Souly et al. 2024.

## 10. Crypto / performance metric engine

`MetricCapture` wraps every `CipherConverter` call and records before the result is returned:

| Metric | Method | Column |
|---|---|---|
| Encryption time | `time.perf_counter()` around `encode()` | `encryption_time_ms` |
| Decryption time | `time.perf_counter()` around `decode()` | `decryption_time_ms` |
| **Avalanche effect** | Flip 1 input bit → P₂; compute `C₁ = encode(P₁)`, `C₂ = encode(P₂)`; count differing bits → `% bits changed` (mean over N=10 trials) | `avalanche_score` |
| **Confusion (χ²)** | Chi-square of ciphertext byte distribution vs. uniform | `confusion_chi2` |
| **Diffusion** | Single-byte input change → spread of bit changes across full output block | `diffusion_score` |
| **Shannon entropy** | `−Σ p_i log₂ p_i` over ciphertext bytes | `shannon_entropy` |
| Target latency | From provider response object | `latency_ms` |
| Token counts | From provider response object | `prompt_tokens`, `completion_tokens` |
| Inferred cost | LiteLLM cost accounting | `cost_usd` |

Unit tests: verify avalanche on a known AES-128 test vector; verify χ² on uniform random
bytes (expected ≈ 255); verify entropy on all-zeros (expected = 0) and random bytes (≈ 8.0).

These become the **independent variables** in the main analytics plot (§11).

## 11. Analytics & the Guardrail Robustness Report

Per-run headline deliverable: a **Guardrail Robustness Report** — exportable HTML/PDF + JSON,
provenance-stamped, screenshot-ready. Aggregate metrics only; never corpus payloads.

**Charts (all filterable by cipher / model / strategy / date):**

| Plot | X axis | Y axis | Why it matters |
|---|---|---|---|
| Payload size vs. encryption time | Plaintext size (bytes) | `encryption_time_ms` | Per-cipher scaling overhead |
| Ciphertext size vs. decryption time | Ciphertext size (bytes) | `decryption_time_ms` | Payload-expansion penalty |
| **Avalanche vs. bypass rate** | `avalanche_score` | bypass rate (%) | **The headline plot** — is crypto strength a predictor? |
| **Entropy vs. bypass rate** | `shannon_entropy` | bypass rate (%) | Companion to avalanche |
| **Evasion cost Pareto** | Bypass rate (%) | `T_enc + T_dec + latency_ms` (+ `cost_usd`) | The economic cost of a bypass |

| Defense ablation *(V1)* | Defense on/off | bypass rate (%) | Does the mitigation work? |
| Judge agreement | Strategy | % agreement across judge/classifier/regex | Methodological rigour |

## 13. Novelties

Ranked by impact-to-effort. Top items = adoption drivers and CV anchors.

1. **Crypto-property → bypass correlation.** Avalanche / diffusion / entropy / χ² as
   predictors of guardrail evasion. No prior cipher-jailbreak tool attaches information-theoretic
   properties to bypass outcomes. This is the signature contribution.

2. **Two-axis success metric.** `filter_evaded` ∧ `semantic_complied` separates "the classifier
   missed the encoding" from "the model couldn't even decode it." More honest than binary bypass;
   directly operationalizes the signature-matching vs. semantic-decoding question.

3. **Curated corpus + vendor-disclosure pipeline.** Confirmed jailbreaks go into a dedicated
   local store, are re-verified against new model versions (`working → patched`), and are
   exported as scoped, provenance-stamped, signed vendor reports. Patch tracking means the
   tool is useful *after* the vendor responds — not just before.

4. **BYOK multi-provider resilience arena + leaderboard.** Point it at any authorized model,
   get a comparable robustness score. Self-hostable, cipher-focused complement to JailbreakBench.

5. **Shareable Guardrail Robustness Report.** One-click, provenance-stamped, screenshot-ready
   aggregate export per model. The artifact that does the awareness-raising.

6. **Attack + defense tradeoff loop.** Pluggable defenses (perplexity filter, Llama-Guard gate,
   paraphrase, retokenization) with on/off ablations — lets a defender verify whether their
   mitigation actually helps.

7. **Evasion-cost economics.** Compute + latency + dollar cost to achieve a bypass. Reframes
   jailbreaks as an economic cost; memorable Pareto plot.

8. **Edge-vs-cloud safety scaling curve.** TinyLlama-on-Pi → Llama3-8B → cloud as a clean
   robustness-vs-model-size plot.

9. **Standards mapping.** OWASP LLM Top 10 + MITRE ATLAS tags on every attack — makes the
   report legible to security practitioners, not just ML researchers.

10. **Reproducibility + interop.** Seeded ciphers, config-as-code YAML, deterministic replay,
    HarmBench/JBB/garak-compatible import/export.

11. **Live SOC-style console.** The streaming view is the README GIF and the demo-day magnet.

## 15. Non-functional requirements

- **Resilience:** 30s hard timeout per target call; HTTP retries with exponential backoff for
  edge/cloud targets; single-model sequential mode for low-VRAM (load/unload between roles).
- **Concurrency:** async attempt execution with a configurable semaphore; respect provider
  rate limits.
- **Determinism:** global `seed` propagates to all cipher shuffles and LiteLLM sampling params
  where supported. Every corpus item must remain byte-reproducible from `seed` + `repro_config_json`.
- **Corpus isolation:** `corpus.db` is opened only by `app/corpus/` and `app/api/corpus.py`.
  All other code paths (analytics, leaderboard, public reports) use `telemetry.db` exclusively.
- **Observability:** structured JSON logs, per-attempt trace IDs, keys always redacted in logs.
- **Security:** the key-leak grep test scans telemetry DB serializations, corpus DB
  serializations, and generated vendor report artifacts.
